# 03. Summary 生命周期

> Summary 是"软索引"——AI 拥有生成权，引擎有防丢失义务

---

## 一、Summary 的定位

在 Diff-Mem 中，Summary 不承载"数据真相"，它服务于两个目的：

1. **检索入口**：让 `diff_mem_search` 的 keywords 匹配能找到节点
2. **快速概览**：让 Agent 在 list/show 时快速了解节点内容，决定是否深度加载

**关键认知**：Summary 可以被概括、可以丢失细节、可以不完全准确——因为它只是索引。**Body 事件流才是真相来源**。如果 Summary 和 Body 冲突，以 Body 为准。

这一定位直接决定了：
- Summary **不需要**像 Body 那样严格保真
- Summary 的更新频率**不需要**跟上 Body 的追加频率
- Summary 更新时，重点不是"完全正确"，而是"不能比旧版本更差"

---

## 二、Summary 的生成

### 首次创建

节点创建时，AI 通过 `diff_mem_create` 提交初始 summary。引擎要求 summary 非空、不超过 500 字符，不做其他校验。

```json
{
  "path": "/projects/alpha/backend",
  "title": "Alpha 后端模块",
  "summary": "Alpha 项目的后端开发模块，负责 API 设计和数据库设计。负责人张三，预计 9 月底完成。"
}
```

### 引擎校验

| 校验项 | 规则 | 失败处理 |
|--------|------|----------|
| 非空 | 不允许空字符串 | 拒绝，要求重新提交 |
| 长度 | 不超过 500 字符 | 拒绝，要求缩短 |
| 格式 | 自然语言，不允许纯 JSON/代码 | 警告但不阻止 |

---

## 三、Summary 的刷新

Summary 不会自动更新。只有当 AI 显式调用 `diff_mem_update_summary` 时才变化。

### 何时应该刷新

AI 应该在这些场景考虑刷新 summary：

| 场景 | 示例 | 是否建议刷新 |
|------|------|-------------|
| 节点状态重大变化 | 项目从开发进入测试 | ✅ 强烈建议 |
| 关键字段被修改 | 负责人从张三变为李四 | ✅ 建议 |
| 积累了大量事件 | Body 超过 20 条未摘要 | ✅ 建议 |
| 日常事件追加 | 每天追加一条进度 | ❌ 不需要 |
| 微调一个字段 | deadline 从 9/30 改到 10/5 | ❌ 视情况 |

**原则**：Summary 是"慢更新"的，一两个事件不应该触发刷新。攒够一批变化再刷。

### 刷新机制：实体移除通知（不是硬阻塞）

**核心思想**：不禁止实体消失，禁止"AI 不知道自己丢了什么"。

引擎不对 summary 做"必须保留全部实体"的硬约束。实体消失是正常现象——负责人变更、方案替代、信息过期都是合理的。引擎要防的不是"丢失"本身，而是"沉默的丢失"。

```
AI 调用 diff_mem_update_summary:
{
  "path": "/projects/alpha/backend",
  "old_summary": "Alpha 项目后端，张三负责，deadline 9/30，API 设计完成",
  "new_summary": "Alpha 后端进入测试，李四接替负责，deadline 10/5",
  "reason": "张三离职，李四接替，deadline 顺延一周，API 设计信息已不重要"
}
```

**引擎执行流程**：

```
第1步：抽取 old_summary 中的关键实体
   → [张三, 9/30, API, 设计完成]

第2步：抽取 new_summary 中的关键实体
   → [李四, 10/5, Alpha, 后端]

第3步：找出消失的实体
   → 消失: [张三, 9/30, API, 设计完成]
   → 新增: [李四, 10/5]

第4步：检查 reason
   → reason 非空且超过 10 字符 → ✅ 放行
   → reason 为空或 <10 字符 → ❌ 拒绝，返回消失实体列表

第5步：放行后，引擎自动向 Body 追加审计事件
```

### 引擎抽取实体的规则

引擎用简单规则（不依赖 LLM）抽取关键实体：

| 实体类型 | 抽取规则 | 示例 |
|----------|----------|------|
| 人名 | 中文 2-3 字 / 英文名 | 张三、Alice |
| 日期/时间 | 日期格式 / 相对时间 | 9月底、2026-09-01、下周三 |
| 数字 | 独立出现的数字 | 5个模块、10万预算 |
| 专有名词 | 大写开头的英文词 / 中文特定词汇 | Alpha、React、数据库 |
| 状态关键词 | 特定枚举 | 开发中、已完成、已归档 |

**引擎不判断语义**，只做字符串级别的实体提取和存在性对比。

### 对比通过的条件

更新通过，当且仅当：
1. **reason 非空且 ≥10 字符**：如果 old_summary 有实体消失，AI 必须在 reason 中解释
2. **reason 不能是敷衍回答**：引擎检测常见敷衍模式（如"不需要"、"没用了"、"none"、"N/A"），匹配则拒绝

**不检查的内容**：
- 不检查"消失的实体是否合理"（引擎没有语义能力，也越界了）
- 不检查"reason 是否真实"（引擎无法验证，信任 AI 的自我报告）
- 不阻止实体消失本身（消失是允许的，沉默才是问题）

**如果校验不通过** → 引擎返回具体的消失实体列表，AI 可以补充 reason 后重试。

### 审计事件的自动追加

每次 summary 更新通过校验后，引擎自动向 Body 追加一条审计事件：

```json
{
  "ts": "2026-09-01T18:30:00Z",
  "type": "summary_update",
  "old": "张三负责后端，deadline 9/30，API 设计完成",
  "new": "李四接替负责，deadline 10/5",
  "removed_entities": ["张三", "9/30", "API", "设计完成"],
  "justification": "张三离职，李四接替，deadline 顺延，API 设计信息已不重要"
}
```

**关键价值**：即使信息从 summary 中消失了，也安全地保存在 Body 的审计日志里。后续 Agent 需要回查时，可以从 Body 中找回这些信息。

## 四、Summary 与 Body 的关系

```
Body（真相）
├── Event 1: 创建项目，负责人张三，deadline 9/30
├── Event 2: 张三离开，李四接替
├── Event 3: deadline 改为 10/5
├── ...
    ↓
Summary（索引，概括自 Body）
"Alpha 后端模块，李四负责，deadline 10/5，API 设计完成"
```

**一致性规则**：
- Summary 可以比 Body 简洁（概括）
- Summary 不能包含 Body 中不存在的实体（幻觉）
- 如果 Agent 发现 Summary 和 Body 矛盾 → 以 Body 为准，触发 summary 刷新

**引擎不主动校验 Summary 与 Body 的一致性**（那需要理解语义，成本高）。一致性校验留给 Agent 发现：
- Agent deep_load 后发现 summary 过时 → 主动刷新
- 用户反馈"你记错了" → Agent 查 Body 修正 summary

---

## 五、Summary 的过期与归档

### 节点归档时

节点 `diff_mem_archive` 后：
- Summary 冻结，不再允许更新
- 但 `diff_mem_show` 仍可读取
- 搜索时默认排除归档节点

### 节点删除时

节点 `diff_mem_delete` 后：
- Summary 随节点一起删除
- 但删除操作本身记录在全局操作日志中

---

## 六、Summary 更新频率控制

为了防止 AI 过度刷新 summary（浪费 token、造成不稳定），引擎做频率限制：

```
单个节点的 summary 更新频率：
- 每小时最多 3 次
- 每天最多 10 次

如果超限 → 引擎拒绝，返回 "更新过于频繁，请稍后重试"
```

**理由**：如果 AI 需要每小时更新好几次 summary，说明它可能在做错事（应该用 append 记录事件而不是刷新 summary）。

---

## 七、设计总结

| 维度 | 设计决策 |
|------|----------|
| 谁生成 | AI 全权决定 |
| 谁校验 | 引擎做新旧对比，防丢失 |
| 更新频率 | AI 触发，引擎限速 |
| 真相来源 | Body，Summary 只是索引 |
| 漂移容忍 | Summary 允许漂移，但不允许比旧版更差 |
| 冲突处理 | 以 Body 为准，Summary 被修正 |

**核心思想**：Summary 是一个"受控的软索引"。AI 有生成权但引擎有把关权。引擎不评判摘要的质量，只确保"不丢东西"。
