# 07. 节点生命周期与归档

> 记忆只有两个状态：活跃和归档。中间没有流程门禁。

---

## 一、记忆节点的两种状态

```
active ──→ archived
  ↑           ↑
  │           │
  └── restore ┘
```

就这么简单。一个记忆节点要么**活跃**，要么**归档**。没有 proposed、implemented、rejected 这些中间态——那套是给文档流转用的，记忆节点不是决策，只是一条记录。

| 状态 | 可以读 | 可以写 | 出现在 search 结果中 |
|------|--------|--------|-------------------|
| active | ✅ | ✅ | ✅ |
| archived | ✅ | ❌（Body 冻结） | ❌（需 include_archived） |

---

## 二、归档的本质问题

归档不是"这个任务做完了"，而是**"这条记忆不再被需要了"**。

两者的区别决定了完全不同的归档逻辑：

```
❌ 文档思维：决策完成 → 归档  （流程终点）
✅ 记忆思维：信息不再被需要 → 归档  （自然衰退）
```

一个记忆节点可能记录了"张三 8 月份负责后端开发"。9 月张三离职了，这条记忆的内容变成了"过去时"。它不需要被归档——它仍然有参考价值（"谁曾经负责后端？"）。但到了明年，连"谁曾经负责"这个信息都不再有场景会被问到——**这才是归档时机**。

---

## 三、归档的判断依据

AI 判断是否归档时，看三个维度：

### 3.1 信息是否已被消费

```
场景 A：节点记录了"待修复的 bug 列表"
         → 所有 bug 修完了
         → 这个 bug 列表本身已无价值
         → 可以归档

场景 B：节点记录了"系统架构决策"
         → 架构还在用
         → 这个决策仍在指导当前工作
         → 不应归档
```

**关键**：不是"内容完成没有"，而是"这条记录本身还有没有查询价值"。

### 3.2 是否还有其他节点引用它

```
节点 A: /decisions/认证方案
节点 B: /projects/alpha/backend    ← references A

A 要归档？
  → B 还活跃且引用 A → A 不宜归档
  → B 已经归档或删除 → A 可以归档
```

引擎在归档时做检查：如果该节点有来自活跃节点的入站引用，返回警告但不阻止（AI 可能判断引用已不重要）。

### 3.3 重新被需要的可能性

```
低概率 → 归档：
  "8 月 3 日团队聚餐菜单"

高概率 → 保留活跃：
  "API 鉴权方案的权衡分析"
```

这个判断纯粹是 AI 的语义能力，引擎不介入。

## 四、归档操作

### 4.1 `diff_mem_lifecycle`

```json
{
  "name": "diff_mem_lifecycle",
  "description": "节点生命周期状态转换。action=archive：归档指定节点。归档后节点冻结，Body 和 Header 均不可修改，从默认搜索中排除，但仍可读。归档是 AI 主动决策，引擎不自动触发。action=restore：恢复已归档节点为活跃状态，重新出现在搜索结果中。",
  "parameters": {
    "action": {"type": "string", "enum": ["delete", "archive", "restore"]},
    "path": {"type": "string"},
    "reason": {"type": "string", "description": "操作原因"}
  }
}
```

**引擎校验**：
- reason 非空
- archive：不能重复归档已归档节点
- archive：检查入站活跃引用，有则返回警告及三选一处置指引
- restore：只有 archived 节点能恢复；恢复时检查出站链接，目标已删/归档 → 警告悬空

**归档后行为**：
- 节点状态变为 archived
- Header 和 Body 冻结
- 自动向 Body 追加归档事件（时间戳 + reason）

### 4.2 恢复

归档不是永久的。AI 通过 `diff_mem_lifecycle(action=restore)` 恢复归档节点。

**恢复后行为**：
- 节点状态变为 active
- Header 和 Body 解冻
- 自动向 Body 追加恢复事件

## 五、节点间的引用：内容链接

记忆节点之间自然存在关联。Diff-Mem 用 **内容链接** 表达关联：直接写在 Body 事件文本里，语法为 `[[/path/to/node]]`。

```
事件文本示例：
"后端模块的方案已定，依赖 [[/Decisions/认证方案]] 的结论"
```

**门禁行为**：

- 写入时（create/append）引擎校验链接目标必须存在，悬空链接直接拒绝，AI 修正后重试
- 读取时（show）返回 `links`（我链接了谁）与 `backlinks`（谁链接了我），AI 看到一条记忆即可发现相关记忆
- 删除被链接的节点 → 拒绝并列出引用方；归档 → 警告但不阻止

详细规则见 01-tool-registry.md §3.8 与 08-content-links.md。

---

## 六、删除 vs 归档

| 操作 | 数据保留 | 可恢复 | 何时用 |
|------|---------|--------|--------|
| archive | 全部保留，冻结 | 可 restore | 不确定未来是否还需要（被链接时警告） |
| delete | 永久删除 | 不可恢复 | 确定永远不需要（被链接时拒绝） |

默认倾向 archive 而不是 delete——记忆宁可多留别误删。

## 七、与 DeepSeek Harness 的根本区别

| 维度 | DeepSeek（文档门禁） | Diff-Mem（记忆系统） |
|------|---------------------|---------------------|
| 状态数 | 4（proposed/implemented/rejected/archived） | 2（active/archived） |
| 归档含义 | 决策流程终点 | 信息自然衰退 |
| 归档触发 | 决策完成后 | 信息不再被需要时 |
| 恢复 | 不可恢复 | 可 restore |
| 核心问题 | "这个决定做完了吗？" | "这条记忆还有用吗？" |
| 引擎角色 | 校验流转合法性 | 校验归档约束 |

**DeepSeek 的 proposed/implemented 对记忆系统没有意义**——一个记忆节点在被创建的那一刻就已经"存在"了，它不需要经历"提议→实施"的流程。记忆是事实的记录，不是待执行的决策。
