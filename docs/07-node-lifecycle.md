# 07. 节点生命周期与归档

> 记忆只有两个状态：活跃和归档。中间没有流程门禁。

---

## 一、记忆节点的两种状态

```
active ──→ archived
  ↑           ↑
  │           │
  └── restore ┘
```

就这么简单。一个记忆节点要么**活跃**，要么**归档**。没有 proposed、implemented、rejected 这些中间态——那套是给文档流转用的，记忆节点不是决策，只是一条记录。

| 状态 | 可以读 | 可以写 | 出现在 search 结果中 |
|------|--------|--------|-------------------|
| active | ✅ | ✅ | ✅ |
| archived | ✅ | ❌（Body 冻结） | ❌（需 include_archived） |

---

## 二、归档的本质问题

归档不是"这个任务做完了"，而是**"这条记忆不再被需要了"**。

两者的区别决定了完全不同的归档逻辑：

```
❌ 文档思维：决策完成 → 归档  （流程终点）
✅ 记忆思维：信息不再被需要 → 归档  （自然衰退）
```

一个记忆节点可能记录了"张三 8 月份负责后端开发"。9 月张三离职了，这条记忆的内容变成了"过去时"。它不需要被归档——它仍然有参考价值（"谁曾经负责后端？"）。但到了明年，连"谁曾经负责"这个信息都不再有场景会被问到——**这才是归档时机**。

---

## 三、归档的判断依据

AI 判断是否归档时，看三个维度：

### 3.1 信息是否已被消费

```
场景 A：节点记录了"待修复的 bug 列表"
         → 所有 bug 修完了
         → 这个 bug 列表本身已无价值
         → 可以归档

场景 B：节点记录了"系统架构决策"
         → 架构还在用
         → 这个决策仍在指导当前工作
         → 不应归档
```

**关键**：不是"内容完成没有"，而是"这条记录本身还有没有查询价值"。

### 3.2 是否还有其他节点引用它

```
节点 A: /decisions/认证方案
节点 B: /projects/alpha/backend    ← references A

A 要归档？
  → B 还活跃且引用 A → A 不宜归档
  → B 已经归档或删除 → A 可以归档
```

引擎在归档时做检查：如果该节点有来自活跃节点的入站引用，返回警告但不阻止（AI 可能判断引用已不重要）。

### 3.3 重新被需要的可能性

```
低概率 → 归档：
  "8 月 3 日团队聚餐菜单"

高概率 → 保留活跃：
  "API 鉴权方案的权衡分析"
```

这个判断纯粹是 AI 的语义能力，引擎不介入。

## 四、归档操作

### 4.1 `diff_mem_archive`

```json
{
  "name": "diff_mem_archive",
  "description": "归档指定节点。归档后节点冻结，Body 和 Header 均不可修改，从默认搜索中排除，但仍可读。归档是 AI 主动决策，引擎不自动触发。",
  "parameters": {
    "path": {"type": "string"},
    "reason": {"type": "string", "description": "归档原因"}
  }
}
```

**引擎校验**：
- reason 非空
- 不能重复归档已归档节点
- 检查入站活跃引用，有则返回警告

**归档后行为**：
- 节点状态变为 archived
- Header 和 Body 冻结
- 自动向 Body 追加归档事件（时间戳 + reason）

### 4.2 `diff_mem_restore`

归档不是永久的。AI 可以恢复归档节点：

```json
{
  "name": "diff_mem_restore",
  "description": "恢复已归档节点为活跃状态。恢复后节点可正常读写，重新出现在搜索结果中。",
  "parameters": {
    "path": {"type": "string"},
    "reason": {"type": "string", "description": "恢复原因"}
  }
}
```

**恢复后行为**：
- 节点状态变为 active
- Header 和 Body 解冻
- 自动向 Body 追加恢复事件

## 五、节点间的引用

记忆节点之间自然存在关联。Diff-Mem 支持显式引用：

```json
{
  "name": "diff_mem_link",
  "description": "在两个节点间建立引用关系。用于记录依赖、关联、替代等关系。",
  "parameters": {
    "from": {"type": "string"},
    "to": {"type": "string"},
    "type": {"type": "string", "enum": ["depends_on", "alternative_to", "supersedes", "references"]},
    "reason": {"type": "string"}
  }
}
```

```json
{
  "name": "diff_mem_unlink",
  "description": "移除两个节点间的引用关系。",
  "parameters": {
    "from": {"type": "string"},
    "to": {"type": "string"}
  }
}
```

**引用在归档中的角色**：

```
AI 要归档节点 A
引擎检查：A 有入站引用吗？
  → 有，来自活跃节点 B
    → 引擎返回警告："节点 /X 仍被 /Y 引用，确认要归档？"
    → AI 可以无视警告继续归档
    → 也可以先 unlink 再归档
  → 无
    → 直接归档
```

## 六、删除 vs 归档

| 操作 | 数据保留 | 可恢复 | 何时用 |
|------|---------|--------|--------|
| archive | 全部保留，冻结 | 可 restore | 不确定未来是否还需要 |
| delete | 永久删除 | 不可恢复 | 确定永远不需要 |

默认倾向 archive 而不是 delete——记忆宁可多留别误删。

---

## 七、与 DeepSeek Harness 的根本区别

| 维度 | DeepSeek（文档门禁） | Diff-Mem（记忆系统） |
|------|---------------------|---------------------|
| 状态数 | 4（proposed/implemented/rejected/archived） | 2（active/archived） |
| 归档含义 | 决策流程终点 | 信息自然衰退 |
| 归档触发 | 决策完成后 | 信息不再被需要时 |
| 恢复 | 不可恢复 | 可 restore |
| 核心问题 | "这个决定做完了吗？" | "这条记忆还有用吗？" |
| 引擎角色 | 校验流转合法性 | 校验归档约束 |

**DeepSeek 的 proposed/implemented 对记忆系统没有意义**——一个记忆节点在被创建的那一刻就已经"存在"了，它不需要经历"提议→实施"的流程。记忆是事实的记录，不是待执行的决策。
