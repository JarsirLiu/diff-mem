# 04. 状态漂移防御体系

> 哪些可以漂、哪些不能漂——Diff-Mem 的防线分层

---

## 一、状态漂移的本质

状态漂移不是 LLM "出错"，而是 LLM 在做"概括"时固有的信息损失：

```
事实: "张三负责后端 API 开发，deadline 9/30，当前已完成 3 个接口"
        ↓ LLM 概括
"张三负责后端开发，快完成了"
        ↓ 再次概括
"张三负责后端，进行中了"
        ↓ 再次概括
"后端开发中"
        ↓ 再次概括
"后端模块"
```

每一步都没"错"，但信息在衰减。累积十几次这样的概括，真相面目全非。

**Diff-Mem 的防御策略**：承认漂移不可避免，但**控制漂移的边界**。

---

## 二、分层防线模型

```
┌──────────────────────────────────────────────┐
│  L0: 不可漂层（Body 事件流）                  │
│  追加即锁定，永不修改                          │
├──────────────────────────────────────────────┤
│  L1: 受控层（Header 字段）                    │
│  可修改，但每次修改有审计日志                  │
├──────────────────────────────────────────────┤
│  L2: 软索引层（Summary / Tags）              │
│  可自由更新，引擎做新旧对比防丢失              │
└──────────────────────────────────────────────┘
```

### L0：不可漂层 — Body 事件流

**规则**：
- APPEND 操作追加的事件**永远不可修改、不可删除**
- 不存在 `diff_mem_update_event` 或 `diff_mem_delete_event` 工具
- 即使 AI 想改某条历史事件，也只能追加一条新事件来"更正"

```
错误做法:
  Body: [Event 1: "deadline 9/30", Event 2: "deadline 9/28"]  ← 直接改了
正确做法:
  Body: [Event 1: "deadline 9/30", Event 2: "deadline 更正为 9/28"]  ← 追加修正
```

**为什么不做事件编辑**：
1. 保持事件的不可篡改性，便于审计
2. 保留"曾经以为 deadline 是 9/30"这个事实本身也有价值
3. 避免了"谁有权限修改历史"这个复杂的权限问题

### L1：受控层 — Header 字段

**可修改的字段**：
- `title`：任意修改，引擎不校验
- `status`：枚举类型，引擎校验状态转换合法性
- `fields.*`：任意修改，每次修改追加到 Body 作为审计事件

**引擎的记录机制**：
每次 `diff_mem_update_field` 执行后，引擎自动向 Body 追加一条审计事件：

```json
{
  "ts": "2026-09-01T18:30:00Z",
  "type": "field_change",
  "field": "deadline",
  "old_value": "9/30",
  "new_value": "10/5",
  "reason": "项目延期"
}
```

这意味着即使 Header 被错误修改，Agent 可以通过 deep_load 查 Body 找回旧值。

### L2：软索引层 — Summary / Tags

**规则见 [03-summary-lifecycle.md](./03-summary-lifecycle.md)**：
- Summary 由 AI 全权生成和更新
- 引擎不阻止实体消失，但要求 AI 在 reason 中解释消失原因
- Tags 类似，但更简单——不做语义校验
- 每次 summary 更新的消失实体和理由自动记录到 Body 审计事件，保证历史可追溯

---

## 三、节点状态

Diff-Mem 的节点只有两种状态：

```
active ──→ archived
  ↑
  └── restore
```

- **active**：可读写，出现在搜索结果中
- **archived**：只读冻结，不出现在默认搜索中，可恢复

节点创建时默认为 active。`diff_mem_archive` 转为 archived，`diff_mem_restore` 转回 active。没有 proposed/implemented/rejected 等中间态——记忆节点是事实记录，不是待执行的决策，不需要流程门禁。

---

## 四、防重复写入

如果 AI 调用 `diff_mem_append` 追加了一条和已有事件**完全相同**的内容：

```
已有: "创建后端模块，负责人张三"
新加: "创建后端模块，负责人张三"
```

**引擎行为**：
- 记录一条去重警告到日志
- 但**仍然执行追加**（不拒绝）

**理由**：完全相同的事件连续出现本身也是信息（说明 AI 可能卡住了、或者用户重复强调了）。让数据说话，让 Agent 自己判断。

---

## 五、防幻觉写入

AI 可能在 summary 或 event 中写入**不存在的实体**：

```
用户没说任何人，AI 却写: "负责人张三说这个很好"
```

**引擎能做的**：
- 不能判断"张三"是否真实存在（引擎不知道张三是否存在）
- 可以在 Body 追加时标记 `confidence` 字段

**引擎可以做的辅助**：
- 当 AI 写入一个人名时，引擎检查 `/people/` 下是否有该人
- 如果没有 → 引擎警告但不阻止（可能是新人）
- 有 `diff_mem_search` 的结果可以提示 Agent "之前没出现过这个人，确认无误？"

**核心认知**：引擎无法完全防幻觉，只能**降低概率**和**增加发现概率**。

---

## 六、回滚机制

如果 AI 做出了错误的写入（比如把 status 从 active 改成 completed 但实际没完成）：

```
AI 可以: diff_mem_update_field("/projects/alpha", "status", "active", reason="上一步误操作，更正")
```

**回滚不是特殊操作，就是普通的字段更新**。引擎不区分"正常更新"和"回滚更新"，两者都记录到 Body。

**全局操作日志**提供完整的变更历史，理论上任何状态都可以还原：
- 读 Body → 找到上次正确状态 → 手动恢复

---

## 七、漂移度量（Phase 2）

引擎可以在后台计算每个节点的**漂移得分**：

```
漂移得分 = 近 100 条事件中，summary 未覆盖的实体比例
```

得分高 → 引擎在 `diff_mem_show` 返回时附带警告：
```json
{
  "success": true,
  "result": { ... },
  "warnings": ["⚠️ 此节点的 summary 可能过时，建议刷新。近 100 条事件中有 47 条涉及 summary 未提及的新实体。"]
}
```

这相当于引擎主动提示 Agent "你该更新 summary 了"。

---

## 八、总结

| 层 | 内容 | 可变性 | 防漂移手段 |
|----|------|--------|-----------|
| L0 Body | 事件流 | 仅追加，永不修改 | 不可变性 |
| L1 Header | 状态/字段 | 可修改 | 审计日志 + 状态机校验 |
| L2 Summary | 摘要/标签 | 自由更新 | 新旧对比防丢失 |

**核心思想**：不试图阻止漂移（因为 AI 总有生成权），而是**限制漂移的影响范围**。真相反复验证时永远有 Body 可查，状态变化永远有审计可追。
