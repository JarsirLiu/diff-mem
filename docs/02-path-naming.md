# 02. Path 命名机制

> AI 决定路径名称，引擎做规范化和冲突控制

---

## 一、核心矛盾

Path 命名的本质矛盾：

```
AI 需要灵活性 ───────── 引擎需要一致性
"我想用 ProjectAlpha" ── "但必须用小写、不能有空格"
"我要建 /客户/张三" ──── "但中文和英文混用会出问题"
"这个叫 /bug修复记录" ── "但下次可能叫 /Bug修复/record"
```

**原则**：AI 有命名权，但命名后必须经过引擎的**规范化合规检查**。AI 不直接写原始字符串到磁盘，而是提交"命名意图"，引擎翻译为规范路径。

---

## 二、规范化流程

```
AI 提交: path = "/Projects/My Project 2026!/Backend-API"
                ↓
第1步 分隔符标准化：空格 → 连字符
         → "/Projects/My-Project-2026!/Backend-API"
                ↓
第2步 去除非法字符：! # $ % & ( ) [ ] { } * ? | < >
         → "/Projects/My-Project-2026/Backend-API"
                ↓
第3步 统一小写
         → "/projects/my-project-2026/backend-api"
                ↓
第4步 去除重复分隔符
         → "/projects/my-project-2026/backend-api"
                ↓
第5步 根目录检查
         → 第一层必须是 /short-term 或 /long-term
                ↓
第6步 检查路径是否已存在
         → 如果存在 → 返回已存在路径，操作失败
         → 如果不存在 → 创建成功（中间目录无需预先创建）
```

---

## 三、规范规则表

| 规则 | 描述 | 示例 |
|------|------|------|
| 全小写 | 所有 path 层级转小写 | `Alpha` → `alpha` |
| 连字符分隔词 | 空格/下划线/换行 → `-` | `my project` → `my-project` |
| 去特殊字符 | 仅保留 a-z, 0-9, `-`, `/`, `_` | `Project!` → `project` |
| 去前后空格 | 每层 trim | ` "Alpha" ` → `alpha` |
| 去空层级 | 连续分隔符合并 | `/a//b///` → `/a/b/` |
| 中文保留 | 中文字符允许，不做 transliteration | `张三` → `张三` |
| 去尾斜杠 | path 末尾不加 `/` | `/a/b/` → `/a/b` |

**保留字符**：`a-z`, `0-9`, `-`, `_`, `/`, 以及 Unicode 中文/日文/韩文字符。

---

## 四、根层级设计：双记忆区

引擎**强制两个根目录**，对应记忆的两类生命周期：

```
/short-term/…    短期记忆区：近期事件、当前任务状态、临时上下文。默认写入这里。
/long-term/…     长期记忆区：经过沉淀、3 个月后仍有价值的内容
                 （用户偏好、项目结构、决策结论、人物关系）。
```

**规则**：
- 所有 path 第一层必须是 `short-term` 或 `long-term`，否则拒绝（`VALIDATION_FAILED`）
- 根目录本身是**虚拟目录**，不是节点——不能对 `/short-term` 做 show/archive/delete
- 中间目录同样是虚拟的：`/long-term/projects/alpha` 可以直接创建，
  `/long-term/projects` 无需预先存在，`list` 按前缀聚合自动可见
- 沉淀流程（由 AI 判断执行）：短期记忆被认为长期有价值时，
  在 `/long-term` 创建沉淀节点，然后归档（archive）短期原件

**设计理由**：
- 短期/长期分离让"什么值得长期记住"成为显式决策，而不是所有信息混在一个空间里自然腐化
- AI 决定内容归属，引擎保证结构——没有第三个根目录，分类漂移无处可藏
- 虚拟目录免去了桩节点的维护成本和搜索噪音

## 五、冲突解决策略

### 5.1 同名冲突

```
AI 请求创建: /projects/alpha
引擎发现已存在: /projects/alpha (标题="Alpha 项目")
```

**处理**：
- 引擎拒绝创建，返回已有路径和 Header
- Agent 需要决定：使用已有节点 vs 换一个名字

### 5.2 近似名冲突（模糊重复）

```
已存在: /projects/alpha
AI 请求: /projects/alpha-project   ← 可能只是表述不同
```

**处理**：
- 引擎做模糊匹配（编辑距离），如果高度相似（>80%）→ 警告但不阻止
- 警告信息："路径 /projects/alpha 已存在且标题为'Alpha 项目'，你确定要创建新节点 /projects/alpha-project 吗？"
- 模型可以自主决定继续创建或改用已有路径

### 5.3 大小写冲突

```
已存在: /projects/Alpha   （如果引擎没有强制小写时的遗留数据）
AI 请求: /projects/alpha
```

**处理**：
- 引擎匹配后识别为同一节点 → 返回已有路径
- 迁移机制：旧数据的大写路径会被自动重定向

## 六、AI 命名建议（Prompt 层）

Tool description 里给 AI 明确的命名指导：

```
Path 命名规范：
1. 使用小写英文，单词用连字符连接
2. 每层含义明确，如 /projects/alpha/backend/api
3. 不要过深（不超过 4 层），不要过平（不要把一切都放根目录）
4. 人物用中文名，如 /people/张三
5. 任务用动词开头，如 /tasks/重构登录模块
6. 日期作为最后一级，如 /decisions/2026-09-01/重构方案确认
```

## 七、Path 与 Title 的区别

Path 和 Title 各司其职：

| 维度 | Path | Title |
|------|------|-------|
| 用途 | 唯一标识 + 分类 | 人类可读的显示名称 |
| 稳定性 | 几乎不变（创建后不再改） | 可以改 |
| 格式 | 严格的规范字符串 | 任意自然语言 |
| 长度 | 尽量短，层级清晰 | 简短但有意义 |
| 中文 | 允许 | 推荐 |

**典型对应**：
```
Path:  /projects/alpha/backend/api
Title: "Alpha 后端 API 模块"
```

AI 同时决定两者，但引擎只校验 path 的格式，title 完全自由。

---

## 八、删除/重命名时的级联影响

Path 是树中其他节点的引用基础。如果删除/重命名一个中间节点：

```
/tree/projects/alpha/backend
                    ├── /tree/projects/alpha/backend/api
                    └── /tree/projects/alpha/backend/db
```

**规则**：
- 引擎不允许直接重命名 path（保持不可变性）
- 需要重命名时：创建新 path → 迁移所有子节点 → 归档旧 path
- 这是一个 diff_mem_exec 事务操作

---

## 九、总结

| 决策层 | 决策内容 |
|--------|----------|
| AI | 命名意图、层级结构、title、是否使用已有节点、短期/长期归属 |
| 引擎 | 格式规范化、冲突检测、双根目录强制、路径不可变 |

**核心思想**：Path 一旦创建就不可变。需要变更时通过"新建+迁移+归档"完成，保证历史操作的 Path 引用始终有效。
